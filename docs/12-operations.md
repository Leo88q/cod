# Эксплуатация: журнал действий, worker и очередь уведомлений

Дата: 04.11.2026. Дополняет документы 09–11; не подтверждает production-деплой.

## Что реализовано

### Транзакционный журнал

`audit_log` фиксирует успешные операции:
- назначение владельца студии;
- бесплатный выпуск карточек оператором;
- подтверждение заказа студией;
- ручной возврат окончательно ошибочного уведомления в очередь.

Изменение данных и аудит выполняются в одной транзакции. Ошибка аудита откатывает изменение. Содержимое запросов, сообщения, подарочные URL, токены и исходные Telegram ID в журнал не пишутся. Для Telegram-актёров сохраняется SHA-256 ID (псевдонимизация, не анонимизация); для общего admin-токена — `admin-token`.

Ограничения: это **не** полный журнал всех действий/попыток входа, не tamper-proof/WORM-хранилище. Общий admin-токен не различает отдельных операторов. Передача владения фиксирует факт изменения студии, но не сохраняет полный before/after-снимок владельца.

- `GET /api/admin/audit?limit=50&before=<id>` — защищённая постраничная выдача (максимум 200).
- `AUDIT_RETENTION_DAYS=90` — срок хранения; очистку выполняет worker. Без worker очистка не происходит.
- Персональный экспорт включает записи, у которых actor соответствует хешу пользователя. При удалении профиля журнал не стирается немедленно; это отражено в privacy и требует юридической приёмки срока/оснований хранения.

### Состояние worker

В `worker_state` хранится heartbeat после очередного прохода задач:
- `missing`: worker ещё не сообщил о себе;
- `ok`: heartbeat свежий, задачи завершились без ошибок;
- `degraded`: heartbeat свежий, но одна или несколько задач завершились ошибкой;
- `stale`: heartbeat старше `max(120 сек, 3 × SCHEDULER_INTERVAL)`.

Также видны число ошибочных задач последнего прохода и включена ли отправка через Telegram. Это не доказывает доставку каждого сообщения. Проверки/очистки scheduler выполняются через `asyncio.to_thread`, не блокируя event loop API; heartbeat доступен из другого процесса с общей БД.

`/ready` по-прежнему проверяет БД, **не worker**: иначе production Compose не смог бы запустить worker, зависящий от готовности API.

### Окончательно ошибочные уведомления

- `GET /api/admin/notifications/failed` возвращает ID/kind/attempts/время, без текста, адресата и подарочных ссылок.
- `POST /api/admin/notifications/{id}/retry` возвращает только запись `sent=-1` в очередь: обнуляет attempts и next_attempt_at, пишет аудит.
- Повторный запрос для уже ожидающей записи — 409; это предотвращает повторное ручное переоткрытие в гонке.
- Доступ только админу. В админке есть просмотр, предупреждение о возможном дубле и кнопка возврата.
- Доставка по-прежнему at-least-once: сбой после отправки Telegram, но до commit может привести к дублю. Перед повтором нужно устранить причину ошибки.

### Метрики и мониторинг

`GET /api/admin/metrics` отдаёт:
- число ожидающих/окончательно ошибочных уведомлений;
- возраст самого старого ожидающего уведомления;
- состояние worker;
- доступность БД;
- HTTP-счётчики **текущего API-процесса**, не суммарные метрики кластера.

Для этого endpoint можно задать отдельный `MONITOR_TOKEN` и передавать его в заголовке `X-Admin-Token`. Этот токен **не** даёт доступа к журналу, текстам уведомлений, повторной отправке или другим административным функциям. Для внешнего runner используйте именно его, а не полный admin-токен.

`scripts/monitor.py` — один проход проверки, без бесконечного процесса:

```sh
# Секреты загрузить в окружение runner, не записывать значениями в командную строку.
python scripts/monitor.py
```

Переменные:
- `MONITOR_BASE_URL=https://ваш-домен`;
- `MONITOR_TOKEN` — отдельный read-only токен (должен совпадать с env API);
- `MONITOR_STATE_PATH=/var/lib/scena-monitor/state.json`;
- `MONITOR_MAX_PENDING=200`;
- `MONITOR_MAX_PENDING_AGE=3600` (секунды).

Совместимость: прежнее имя `MONITOR_ADMIN_TOKEN` поддерживается, но использование полного админского секрета не рекомендуется.

Проверяется `/ready` + метрики: worker, backlog/возраст очереди, dead letters, отсутствие доставки при непустой очереди и новые 5xx с предыдущего запуска. Состояние счётчика сохраняется атомарно; secret/URL/тела сообщений не печатаются, редиректы не разрешены. HTTPS обязателен, кроме localhost для smoke.

Коды завершения: `0` — проверки прошли; `1` — alert или ошибка проверки; `2` — неверная базовая конфигурация.

**Внешний runner и доставка алертов не настроены автоматически.** Запускайте на отдельном хосте по cron/systemd timer и подключите уведомление по ненулевому exit status в своей системе мониторинга. Если запускать только на том же сервере, падение всего хоста не будет обнаружено. При нескольких API workers требуется общий сбор метрик (Prometheus/другой агрегатор); локальный счётчик не является полной системой 5xx-мониторинга.

## Интерфейс и проверки

В админку добавлены состояние worker, ошибка доставки, ручной повтор и последние 50 записей журнала. DOM-тест также выявил и закрыл незагруженную переменную `tcs`, мешавшую отрисовке очереди таймкодов.

- **69 Python-тестов**: в том числе откат retry при ошибке аудита, недопуск постороннего, повторный retry, heartbeat/degraded/stale, TTL журнала, назначение владельца и read-only изоляция monitor-токена.
- **7 DOM-тестов**, включая операционный экран админки.
- Общий `bash scripts/check.sh` включает тесты и проверки синтаксиса.

## Остающиеся задачи

Полная именная ролевая модель операторов, защищённое от изменения внешнее хранение аудита, реальные alert-каналы, offsite runner и кластерная агрегация метрик остаются открыты. Платёжные возвраты/чеки, браузерные проверки, нагрузочный профиль и фактический production-деплой этим пакетом не заменены.
